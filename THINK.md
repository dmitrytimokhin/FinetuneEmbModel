# THINK.md — Размышления: почему мы делаем именно так

> Здесь не «как запустить», а **«почему именно так»**.
> Разбираем неочевидные решения, ловушки и компромиссы.

---

## 1. Как работает эмбеддинг — мысленная модель

Представьте, что каждый текст — это точка в многомерном пространстве.
1024 чисел = координаты этой точки. «Близкие» тексты стоят рядом.

```
       [страхование жизни]
              ↑
              |  ←← как далеко стоят эти точки — это и есть качество модели
              |
[ипотека] ←──┼──→ [автокредит]
              |
              ↓
       [интернет-банк]
```

Стандартная модель после предобучения помещает «ипотеку» и «автокредит» достаточно
близко — обе про кредиты. После дообучения они должны разойтись настолько,
чтобы запрос про ипотечную ставку не находил документ про ставку по факторингу.

**Ключевая идея**: мы не учим модель «знать факты».
Мы учим её **структурировать пространство** так, чтобы похожие смыслы стояли рядом.

## 2. Положительные и отрицательные примеры: спектр трудности

### Что такое «трудный» негатив и зачем он нужен

Градиент (то, на что обучается модель) равен нулю для «слишком лёгких» примеров.
Если негатив — «рецепт борща» на запрос про ипотеку — модель уже отличает их,
обучения нет. Нужны примеры, где модель **ошибается**.

```
                              Слишком лёгкий    Оптимальный       Слишком трудный
                                    │               │                    │
Случайный   BM25-hard        Embedding-   False negative
из         из другого        hard (ANCE)   (реально
корпуса    документа                       релевантен)
───────────────────────────────────────────────────────────────────────────────►
     нет градиента           золотая зона         нестабильное обучение + шум
```

**BM25-hard** — наш выбор. Лексически похожие тексты из другого документа.
Модель видит много общих слов, но должна понять, что смысл другой.

Пример:
```
anchor:   "каков порядок досрочного погашения ипотеки"
negative: "каков порядок досрочного погашения потребительского кредита"
          ↑ Слова почти одинаковые, но документ другой — это трудный негатив
```

### Ловушка: False Negative

Самая опасная ошибка в данных — **false negative**: мы говорим модели «это неправильный ответ»,
хотя он правильный.

```
anchor:   "минимальный первоначальный взнос по ипотеке"
negative: "первоначальный взнос составляет от 15% стоимости объекта"
          ↑ ЭТО ПРАВИЛЬНЫЙ ОТВЕТ. Но мы пометили как негатив!
```

Модель получает сигнал «отталкивай эти два вектора» — и учится неправильному.

**Как мы избегаем**: негативы берутся только из **другого документа**.
Это не гарантирует 100% корректность, но значительно снижает риск.

## 3. Три стратегии формирования пар: что лучше для банка

### Adjacent (соседние абзацы)

```python
anchor   = "Ставка по ипотеке зависит от первоначального взноса..."
positive = "Первоначальный взнос составляет не менее 15%..."
```

В линейных текстах (научные статьи, новости) это работает: соседние абзацы
связаны по смыслу. **В банковских документах — ловушка**:

```
Документ "Условия ипотеки":
├── Требования к заёмщику          ← абзац 1
├── Процентные ставки              ← абзац 2  (anchor)
├── Обязательное страхование       ← абзац 3  (positive???)
└── Досрочное погашение            ← абзац 4

anchor = "ставка по ипотеке"
positive = "страхование обязательно" ← смежный текст, но НЕ отвечает на вопрос
```

Банковские документы **дискретны** по смыслу. Страхование — отдельная тема.
Соседство по позиции ≠ семантическое сходство.

Вывод: `adjacent` используем только с фильтром по `section`, иначе — шум.

### Section (один раздел)

Если в документе есть явная структура разделов, все чанки внутри раздела
действительно связаны:

```
Секция "Ипотека / Ставки":
├── "Базовая ставка по ипотеке — 11% годовых"
├── "Льготная ставка по программе семейной ипотеки — 6%"
└── "Ставка при первоначальном взносе >30% снижается на 0,5 п.п."
```

Все три — про ставки. Пары (любой, любой из этих трёх) = хорошие positives.

Но если документ монотематичен и не имеет разделов — стратегия не работает.

### Query Template (шаблонные запросы)

```python
chunk  = "Льготный период по кредитной карте составляет 55 дней..."
anchor = "Каков льготный период кредитной карте?"  # шаблон: "Каков {тема}?"
```

**Почему это лучший вариант**: anchor гарантированно задаёт вопрос,
на который именно этот чанк является ответом. Нет false positives.

**Ограничение**: шаблон извлекает первые 5 слов чанка как «тему».
Иногда это не работает. Решение — генерировать запросы через LLM.

## 4. TSDAE: почему он нужен и как работает на самом деле

### Оригинальная идея

Берём предложение, случайно удаляем 60% слов (corruption) и обучаем модель
восстанавливать оригинал из зашумлённой версии. Encoder кодирует зашумлённое,
decoder восстанавливает оригинал.

```
"кредит без залога нужен справки справка доход"
                 ↓ encoder
              [вектор]
                 ↓ decoder
"Потребительский кредит без залога: нужна справка о доходах"  ← исходный текст
```

**Для правильного восстановления encoder должен понять смысл**, а не запомнить форму.
Именно это и нужно — семантическое понимание банковских текстов.

### Проблема с новыми версиями transformers

Оригинальный TSDAE использует encoder-decoder архитектуру (seq2seq).
Но `deepvk/USER-bge-m3` — encoder-only модель (как BERT).
В `transformers >= 5.0.0` привязка весов encoder и decoder сломана.

**Наше решение — SimCSE-стиль**: используем пары (зашумлённый, оригинал)
с MultipleNegativesRankingLoss. Encoder кодирует зашумлённую версию,
она должна быть близка к эмбеддингу оригинала.

```
sim(encoder("кредит нужен справки"), encoder("Потребительский кредит без залога...")) → высокое
sim(encoder("кредит нужен справки"), encoder("Ставка по ипотеке...")) → низкое
```

Это работает аналогично TSDAE для целей доменной адаптации.

## 5. In-batch negatives: хитрость MNRL

Обычный подход: для каждого anchor хранить явный негатив.
MNRL делает умнее: positives других примеров в батче — автоматически негативы.

```
Батч из 4 пар:
  (q1, p1)  ← q1 ищет p1
  (q2, p2)  ← q2 ищет p2
  (q3, p3)  ← q3 ищет p3
  (q4, p4)  ← q4 ищет p4

Для q1: positive = p1, negatives = {p2, p3, p4} — автоматически!
```

При `batch_size = 32` → каждый запрос видит 31 негатив на каждом шаге.
При 1000 шагах за эпоху = 31 000 уникальных отрицательных примеров.

**Критически важно**: при MNRL в батче не должно быть дублирующихся текстов.
Если `p1 == p3`, то для `q1` p3 — это false negative.
Поэтому используется `BatchSamplers.NO_DUPLICATES`.

**Зависимость от batch_size**: при `batch_size = 4` → только 3 негатива.
Модель учится слабо. На CPU мы вынуждены работать с `batch_size = 4`,
но компенсируем через `gradient_accumulation_steps = 8`:
накапливаем градиенты от 8 батчей, получая `effective_batch_size = 32`.
Эмбеддинги пересчитываются каждый батч, но шаг оптимизатора — раз в 8 батчей.

## 6. Температура в MNRL: что такое τ и зачем её трогать

```python
L = −log( exp(sim(a, p) / τ) / Σ exp(sim(a, p_j) / τ) )
```

Температура τ = 0.05 — это масштаб. Чем меньше τ, тем «острее» распределение:

```
τ = 1.0:  sim_scores = [0.8, 0.6, 0.5, 0.4] → softmax ≈ [0.35, 0.26, 0.22, 0.17]
          (размыто, модель не уверена в правильном ответе)

τ = 0.05: sim_scores / τ = [16, 12, 10, 8] → softmax ≈ [0.98, 0.018, 0.002, 0.000]
          (резко, модель очень уверена, что 0.8 — правильный)
```

Малая τ = жёсткое требование к разделению. Хорошо для retrieval,
где нам нужна чёткая граница «релевантно / нерелевантно».

**τ = 0.05 — стандарт** для всех retrieval-моделей (E5, BGE, INSTRUCTOR).

## 7. Ранняя остановка: почему loss растёт обратно

Типичная картина при дообучении маленького датасета:

```
Эпоха:  1    2    3    4    5    6    7    8
Loss:  2.1  1.8  1.6  1.5  1.6  1.7  1.8  1.9
                       ↑
                    Переобучение начинается здесь
```

Модель «заучивает» обучающие примеры, теряя обобщающую способность.
На eval_loss это видно раньше, чем на train_loss.

**Supervised**: используем `EarlyStoppingCallback` из transformers.
Он мониторит `eval_loss` и останавливает при отсутствии улучшения N эпох.
Автоматически загружает лучший чекпоинт.

**Unsupervised (TSDAE)**: у нас нет eval_dataset (нет разметки).
Используем кастомный `_EarlyStoppingOnTrainLoss`:
- Мониторит `train_loss` через `on_log` callback
- При улучшении → сохраняет модель в `best_unsupervised/`
- После остановки → загружает лучшую модель

## 8. Почему двухэтапный пайплайн лучше одного этапа

Аналогия: вы учите иностранца работать в банке.
Можно сразу учить его отвечать на клиентские вопросы —
но он не знает банковских терминов и будет путаться.
Лучше сначала научить язык (TSDAE), потом — работу (MNRL).

**Техническая причина**:
- MNRL обучает на парах запрос → документ.
- Если модель не понимает слов в документе — градиенты слабые и нестабильные.
- TSDAE сначала «настраивает» пространство эмбеддингов на банковский язык.
- После этого MNRL получает более осмысленное начальное состояние.

Прирост от двухэтапной стратегии: **+5–15% Recall@5** по сравнению с только MNRL.

## 9. Метрики: почему Recall@5, а не точность

В информационном поиске нет понятия «правильный/неправильный ответ» как в классификации.
Есть «попал ли правильный документ в топ-k».

```
Запрос: "как подтвердить доход для ипотеки"

Top-5 результатов:
  1. "Для получения ипотеки требуется справка 2-НДФЛ..."  ← ПРАВИЛЬНЫЙ
  2. "Требования к заёмщику автокредита..."
  3. "Открытие расчётного счёта ИП..."
  4. "Ипотека с господдержкой под 6%..."
  5. "КБМ при ОСАГО..."

Recall@5 = 1 (правильный ответ на 1-м месте)
Recall@1 = 1
MRR@10   = 1/1 = 1.0
```

**Важность для RAG**: LLM читает top-5 чанков и формулирует ответ.
Если правильного нет в топ-5 — LLM либо ошибётся, либо скажет «не знаю».
Поэтому **Recall@5 = насколько часто у LLM вообще есть шанс ответить правильно**.

MRR (Mean Reciprocal Rank) — дополнительная метрика. Если правильный на 2-м месте,
это лучше, чем на 5-м. MRR это фиксирует, Recall — нет.

## 10. Что означают результаты тепловых карт

При первом сравнении (baseline vs TSDAE) мы видели:

```
Оригинал:  внутри темы = 0.498,  между темами = 0.437,  разрыв = 0.061
TSDAE:     внутри темы = 0.146,  между темами = 0.068,  разрыв = 0.078
```

Абсолютные значения упали — это нормально. Модель «растянула» пространство:
теперь похожие тексты занимают меньшую долю гиперсферы.

**Важен не абсолют, а соотношение**:

```
Оригинал: 0.498 / 0.437 ≈ 1.14x  — внутри темы лишь чуть ближе, чем между темами
TSDAE:    0.146 / 0.068 ≈ 2.15x  — внутри темы в два раза ближе, чем между темами
```

Дискриминабельность выросла в 2 раза. Но это промежуточная метрика.
Окончательный вывод — только по Recall@k на реальных запросах.
