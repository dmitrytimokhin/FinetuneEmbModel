# Размышления: как правильно выбирать Positive и Negative

---

## Negative

### Спектр от лёгкого к сверхтяжёлому

```
Случайный       BM25-hard       Embedding-hard     False negative
из корпуса      из другого      близкий по          (это на самом деле
(другая тема)   документа       эмбеддингу          релевантный чанк)

───────────────────────────────────────────────────────────────────►
    слишком легко                              слишком трудно
    модель ничему не учится          нестабильное обучение / шум
```

### Разбор каждой стратегии

**Случайный из другого документа**
Модель легко отличает по теме. Градиент почти нулевой уже после 1–2 эпох.
Использовать только для быстрой проверки работоспособности пайплайна.

**Из того же документа, другая секция / далёкий абзац**
Лучше случайного: тема близкая, терминология пересекается. Хорошо для старта обучения.
Проблема: если документ монотематичен (весь про ипотеку) — все секции релевантны → много **false negatives**.

**BM25-hard из другого документа**
Высокое лексическое сходство с anchor, но другой документ.
Модель должна понять семантику, а не просто ключевые слова.
Рабочая лошадка — используется в DPR, BGE, E5. Стабильно и воспроизводимо.

**Embedding-hard (ANCE / динамический mining)**
Находим чанки, которые **текущая модель** считает похожими, но нерелевантны.
Самые информативные градиенты. Требует переиндексации корпуса каждые N шагов.
Используется во всех SOTA-моделях retrieval.

**In-batch negatives (для MNRL)**
Positives других запросов в батче становятся негативами автоматически.
При `batch_size=64` → 63 негатива бесплатно. Качество растёт вместе с размером батча.

### Главная опасность — False Negative

Чанк из того же документа / соседний абзац могут быть **на самом деле релевантны** anchor:

```
anchor:   "каков минимальный взнос по ипотеке"
negative: "первоначальный взнос по ипотеке — от 15%"  ← правильный ответ!
```

Мы штрафуем модель за правильный ответ. Особенно опасно для стратегий
«соседний абзац» и «тот же документ».

### Рекомендованная стратегия по этапам обучения

| Этап | Стратегия | Почему |
|------|-----------|--------|
| Тёплый старт (1–2 эпохи) | Случайный + BM25-hard | Стабильно, нет взрывных градиентов |
| Основное обучение | BM25-hard + in-batch (MNRL) | Хорошее соотношение качества и стоимости |
| Финальная полировка (GPU) | Embedding-hard (ANCE) | Переиндексация корпуса каждые 500 шагов |

### Вывод для банковских документов

```
Лучший негатив = BM25-hard из ДРУГОГО документа, но ТОЙ ЖЕ финансовой темы

Пример:
  anchor:   "ставка по ипотеке"
  positive: "ставка по ипотеке — от 8,5% годовых по стандартной программе"
  negative: "ставка по потребительскому кредиту — от 9% годовых"  ✓

НЕ делать:
  negative: второй абзац того же ипотечного документа  ← почти всегда false negative
  negative: текст из нерелевантной области             ← слишком легко
```

Соседний абзац из того же документа — **плохой негатив** для банка, потому что
банковские документы монолитны по теме. Это не художественный текст, где соседние
абзацы могут быть о разном.

## Positive

### Главная проблема — не сложность, а релевантность

У негатива риск — «слишком лёгкий» (нет градиента).
У позитива риск — **false positive**: считаем чанк релевантным, а он не отвечает на anchor.

```
anchor:   "какой размер первоначального взноса по ипотеке"
positive: "страхование имущества при ипотеке является обязательным"
          ← из того же документа, но не отвечает — это false positive
```

Модель получает сигнал «приближай эти два вектора» — и учится неправильному.

### Спектр от слабого к сильному

```
Случайный        Тот же         Соседний       Аугментация    Синтетический
чанк того же     раздел         абзац          (SimCSE)       запрос → чанк
документа        (section)      (i±1)

─────────────────────────────────────────────────────────────────────────────►
  много false    зависит от     хорошо для     почти          идеальный
  positives      структуры      линейных       идеально       сигнал
                 документа      текстов
```

### Почему «соседний абзац» плохо работает для банка

В линейных текстах (научные статьи, новости) соседние абзацы связаны по смыслу — хороший positive.
В банковских документах структура **дискретная**:

```
Документ "Условия ипотеки"
├── Абзац 1: требования к заёмщику
├── Абзац 2: процентные ставки          ← anchor про ставки
├── Абзац 3: обязательное страхование   ← сосед, но НЕ отвечает на вопрос
└── Абзац 4: досрочное погашение        ← тоже сосед, тоже мимо
```

Соседство по позиции ≠ семантическое сходство в банковских документах.

### Разбор каждой стратегии

**Любой чанк того же документа** — очень высокий риск false positive.
Весь документ про ипотеку, но не каждый абзац отвечает на конкретный вопрос.

**Та же секция документа** — хорошо, если у документов есть чёткая структура разделов.
Все чанки внутри раздела «Ипотека / Ставки» отвечают на один класс запросов.

**Соседний абзац с фильтром по секции** — приемлемо.
Использовать соседа только если он из той же именованной секции. Без фильтрации — лотерея.

**Аугментация одного чанка (SimCSE-стиль)** — один чанк дважды через encoder
с разными dropout-масками. Гарантированно релевантный positive. Требует специальной
реализации в forward pass.

**Синтетический запрос → чанк** — лучший вариант.
Чанк сам является ответом, запрос генерируется по нему (шаблон или LLM).
Нет false positives по определению.

```python
chunk = "Льготный период по карте составляет до 55 дней при условии..."
query = "сколько дней льготный период по кредитной карте"
# positive = chunk  ← 100% релевантен
```

### Итоговая таблица для банковских документов

| Стратегия | Качество | False positive риск | Нужна разметка |
|-----------|----------|---------------------|----------------|
| `query_template → chunk` | ★★★★★ | нет | нет |
| Та же секция | ★★★★☆ | низкий | нужна структура doc |
| Соседний абзац + фильтр секции | ★★★☆☆ | средний | нужна структура doc |
| Соседний абзац без фильтра | ★★☆☆☆ | высокий | нет |
| Любой чанк того же документа | ★☆☆☆☆ | очень высокий | нет |

### Вывод

Для банковских документов стратегия `query_template → chunk` — лучшая:
шаблонный запрос по чанку гарантирует релевантность positive.
Стратегия `adjacent` подходит только если у документов есть явная разметка секций
(`section != ""`), и сосед фильтруется по совпадению секции с anchor.
Без этого условия `adjacent` даёт много шума.

## Связь positive и negative

Качество пары (positive, negative) важнее качества каждого по отдельности.
Идеальный триплет для банка:

```
anchor:   синтетический запрос по чанку X
positive: чанк X (тот, из которого генерировался запрос)
negative: BM25-hard из другого документа, но той же финансовой тематики
```

Это даёт максимальный информативный градиент: positive гарантированно релевантен,
negative достаточно труден чтобы модель не игнорировала его.
